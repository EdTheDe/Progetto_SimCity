15The project
A ''SimCity Lite'' Engine
Citylogic is a rule-based simulation engine where users
manage a city's growth through strategic policy and
infrastructure placement.
Unlike visual games, the focus is on the Domain Model: how
buildings, resources, and policies interact in a complex object-
oriented environment.
The goal is to optimize "City Health" (Happiness, Economy,
Budget, Population, Pollution, …). over a series of simulation
"ticks".
4/22/2026
Exam project
16Main functionalities
The Urban Grid
•Grid Representation: A logic-based map (e.g., 20x20 cells).
•Object Placement: Ability to "build" different types of entities on the grid:
• Buildings: Residential (houses), Industrial (factories), Commercial (shops).
• Infrastructure: Power plants, parks, roads.
•Resource Management: Every object placed must impact a central "City State" (e.g., Factories
increase Money but also increase Pollution; Parks decrease Money but increase Happiness).
The Simulation Engine
•The "Tick" Mechanism: A command that advances time by one unit (e.g., "Step to Next Month").
•State Update: In each tick, the engine must iterate through the grid and update global metrics (Budget,
Population, Pollution, Happiness).
•Rule Enforcement: Basic logic such as "Residential zones don't grow if there is no Power Plant
nearby.”
4/22/2026
Exam project
17Main functionalities
Policy & Strategy System
•Active Ordinances: The user must be able to activate at least two different "City Policies" (e.g.,
Environmental Tax vs. Industrial Expansion).
•Pattern Requirement: implemented using the Strategy Pattern. The calculation of pollution or income
should change dynamically based on the active strategy.
Persistence (File I/O)
•Save/Load: Ability to save the current grid and city stats to a file (JSON or XML) and reload it later. This
replaces the need for a database.
Visual "Dashboard"
a simple dashboard using Java Swing or JavaFX to show real-time graphs of city growth can help in the final
presentation.
•Constraint: The UI must be strictly separated from the logic (MVC/Clean Architecture).
4/22/2026
Exam project
18Optional functionalities
Dynamic Event System Random Events:
Implement random occurrences like "Fires," "Economic Crashes," or "Heatwaves."
•These events "Notify" relevant buildings or systems (Observer Pattern). For example, a "Heatwave"
notifies all buildings to double their energy consumption.
Citizen Satisfaction Model
Instead of a global happiness score, create a Citizen or PopulationGroup class with specific needs
(Jobs, Health, Safety).
•This allows for a richer Domain Model with more complex interactions.
Web "Dashboard"
Use Spring Boot for presentation instead of Java Swing or JavaFX

21Dos
• Do focus on abstraction: Use inheritance and interfaces for buildings (e.g., abstract class Building, interface PowerConsumer).
• Do use Patterns, e.g.
•Strategy Pattern: for "City Ordinances." Switching from a "Fossil Fuel Policy" to a "Green Policy" should be as simple as swapping a strategy
object.
•Factory Pattern: Ensure your simulation engine doesn't know the concrete classes of the buildings it creates.
•Observer Pattern: Your "Dashboard" or "Status Logger" should be an observer of the City state, ensuring low coupling.
• Do use AI for "Pair Programming": Use AI to generate boilerplate, but specifically prompt it to follow the GoF/GRASP
principles
• Do document your Prompts: Keep a small log of how AI helped you move from a Requirement to a Design and finally to Code.
• Do use AI for Unit Testing: Ask AI to generate edge-case tests (e.g., "What happens to the simulation if the budget becomes
negative?").
• Do maintain Jira daily: Your 10-15 User Stories must reflect the actual progress. Don't create them all at the end of the 40
days.
• Do use GitHub correctly: Use branches and Pull Requests. A single giant commit at the end of the project is a major red flag.

22Don’ts
• No Databases: Do not use MySQL, PostgreSQL, or MongoDB. These introduce "impedance
mismatch" problems that distract from object design. Use memory structures (Lists, Maps) and
simple File I/O.
• No Low-Code App Builders: Avoid tools like Bubble or Lovable for the final delivery. They are
great for prototyping ideas, but they hide the object-oriented design we are evaluating.
• Don't "Copy-Paste-Forget": Never include AI-generated code that you cannot explain line-by-line.
If you can't motivate why a specific pattern was used, it's considered a failure in the design process.
• Don't skip the Design Phase: Do not ask AI to "Write the whole app." Instead, ask it to "Suggest a
class hierarchy for these 3 specific user stories."
• Avoid the City class doing everything: Do not put tax calculations, building logic, and file saving
all in one class. This violates the GRASP Creator and Information Expert principles.

25Inspirational resources
Micropolis-Java
What it is: A Java port of the original SimCity source code.
Why study it: It shows how to handle a large grid of objects (Tile objects) and how a simulation
"engine" iterates through them to calculate effects (pollution, fire risk, growth).
SE Focus: Look at the Engine and CityLocation classes to see how domain logic is separated
from state.
Mars-Simulation-Project
What it is: A highly complex scientific simulation of a Mars settlement.
Why study it: It is a masterclass in the Observer Pattern and Factory Pattern. Every settlement
component is an object that consumes resources.
SE Focus: Observe how they use "Ticks" to advance time and how various System objects (Air,
Water, Power) interact without being tightly coupled.
Open-City-RPG-Backend
What it is: Various Java-based city "backends" found under the GitHub "City Simulation" topic.
Why study it: These often show how to implement File I/O (saving/loading city data) using JSON.
